New Interactive explainer · Oct 2026

How a differential works

A car's open differential on a test bench, running live in the page. Move across it to steer: the gold spider gears start spinning on their pin, one wheel speeds up and the other slows down by exactly as much, and the ring gear keeps turning at their average.

Every number on the readout comes from the real gear ratios (a 41:11 ring and pinion, 16- and 10-tooth bevel gears) and a 1.6 m track. The whole machine is SVG redrawn every frame, and the drawing order of its 46 parts was checked by ray-casting about 7,000 overlaps at 48 angles.

  • SVG
  • Isometric projection
  • Gear kinematics
  • Vanilla JS

Built with Claude Code and its anatomy skill. I chose the subject; Claude designed the machine and wrote the code.

(04) How I work

Four rules I keep
re-learning the hard way.

“A menu entry is not a download. A download is not a working model. A working model is not a good result.”

From building SimoAI
  1. 01

    Ship, then fix

    I built Workspace OS and SVVVD in a single day each. Not because I'm fast, but because I'd rather ship something real and fix it than plan forever and build nothing.

  2. 02

    Evidence that matches the claim

    A passing mocked test isn't a saved file on Windows. The best fixes in SimoAI came from a specific reproduction, a narrow change, and a real check.

  3. 03

    Systems over features

    Data models, constraints and failure modes come first: who owns what, what happens offline, and what the database refuses even if the UI is bypassed.

  4. 04

    Direct the tools, own the result

    I use AI agents like a team: a clear brief, hard constraints, real tests. The code is only as good as the questions I ask and the bugs I catch, so I say plainly which projects were built that way.

Case study · 01 · Local AI

SimoAI

I wanted my own AI assistant before the end of the year, starting with no AI knowledge at all. Within three weeks it was a local, multi-model app: one model plans, specialists do the work, and the interface tells the truth about what actually ran.

When
25 Sep – 12 Oct 2026
My role
Product owner, tester, architect of the routing idea
Built with
An AI coding agent (Codex) writing the implementation
Hardware
i5-14500 · 32 GB RAM · RTX 5060 Ti 16 GB

The first choice

I started with two ideas: a personal chatbot, and a site called BuildAI that would teach beginners to build one. I built the real chatbot first, so that any course later would come from a real beginner's journey and not an invented one. I also dropped "train my own ChatGPT". The realistic goal was a local app built on existing open models.

We set the roles early. I would choose features, test, report failures and learn at a beginner's pace, and the agent would write the code and explain it. Almost every feature below exists because I tested something and it broke.

What it does

  • Chat with Qwen3 14B through Ollama, entirely on the PC.
  • Auto mode: Qwen3 14B plans up to six tasks across chat, code, vision, images, video, diagrams and motion graphics, and hands each one to a specialist.
  • Code with Qwen3-Coder 30B, split across GPU and system RAM.
  • Vision with Gemma 3 12B for image attachments.
  • PDF reading: extracts selectable text (up to 50 pages / 50,000 characters) and renders the first five pages for a vision model when a PDF is scanned.
  • Images with Qwen-Image 2.1 and FLUX.1 Schnell, and video with Wan 2.2 (text-to-video and image-to-video), all through ComfyUI.
  • History in IndexedDB. Every conversation keeps its own model and settings and can be searched, renamed or exported as Markdown.
  • One-click start from a desktop shortcut, and a Quit button that shuts down only the processes SimoAI itself started.

How the system works

The GPU queue matters most. A 16 GB card can't hold a 30B coder, an image model and a video model at once, so jobs run one at a time and idle image models are released before text work. Each result is shown the moment it's ready, so a slow video never blocks the written answer.

Made on my GPU

Three bugs that shaped it

The circle request

I asked Auto mode to explain the area of a circle, draw a blue circle with the formula, and animate a dot growing into a circle. I got an unrelated office scene and lost the written answer. Fix: requests are split into explicit tasks, the text answer comes first, and exact geometry goes to a precise renderer instead of a diffusion model. The same request then finished in 48 seconds with all three outputs.

The 40-minute video

One "quality" run spent about 33 minutes inside Wan rendering 121 frames at 1280×1216. Fix: a 25.6-million pixel-frame budget, roughly 2-second defaults, and GPU text encoding with offload. A controlled 49-frame test dropped from about 3 min 20 s to 2 min 22 s. That's faster, though the video quality still isn't where I want it.

The save that "passed"

A generated image failed to save with a Windows permission error. The first fix passed a mocked test and then failed a real one. Fix: ComfyUI's input, temp and output folders were moved inside the project, with read-only access kept for older images. It was verified with a real generation through SimoAI's own API, and 19 of 19 tests passed.

Measured, not assumed

I set up a head-to-head on a parser task, and a free cloud chatbot clearly beat SimoAI. Instead of concluding "local models are bad", we built a small benchmark: eight JavaScript tasks with hidden test groups, one attempt each, temperature 0, fixed seed.

52 / 65 hidden test groups · 4 / 8 tasks fully passed

It was strong on an LRU cache, interval merging, dependency sorting and safe nested lookup, and weak on command parsing, a CSV edge case, debounce and deep equality. It's a small local benchmark, not a leaderboard. The lesson is that it's good for routine code, but its output still needs tests, especially around parsers.

Honest limits

  • LTX-2.5 video is fully wired into the app, but its gated weights were never installed, so the UI reports it as unavailable instead of pretending.
  • Video quality is still the weakest part. A finished MP4 proves the pipeline ran, not that the motion looks good.
  • An 80B coding model didn't fit: it needed about 38 GiB of system RAM on a PC with 31.7. I removed it and wrote down why.
  • I never weakened Windows security or pasted secrets to make something run, even when that was the shortcut.

What I learned

A useful AI assistant is a system, not one giant model. It needs an interface, model runners, data handling, status checks, safe credentials, routing, media storage and tests. A router model can coordinate everything, but only if it keeps every deliverable the user asked for and makes dependencies explicit.

Most of all, I learned to use evidence that matches the claim. A menu entry isn't a download, a download isn't a working inference, and a working inference isn't a good result.

Case study · 02 · Game

Ironline

How close can a browser get to a competitive tactical shooter? Ironline is an original 5v5 plant-and-defuse game with abilities, an economy and bots that trade, lurk and save. Every name, model and sound in it is original.

When
Sep – Oct 2026
My role
Game direction, scope, acceptance
Built with
An AI coding agent (Claude Code)
Stack
TypeScript · Vite · Three.js · Web Audio · WebSockets

Where it came from

The first attempt, Vector Strike, had one map, four weapons and solo play against bots. It was fun, and it showed exactly what was missing. Rules lived inside the rendering code, bots were easy to read, and nothing could be tested without playing. Ironline started from those lessons, with a clean-room rule: inspired by the genre, but every asset and name original.

Architecture

InputSimulation
128 Hz, deterministicRenderer
Three.js
Writes to simBots · nav gridNet · host-authoritative
Reads from simHUD & minimapSpatial audio
Checks the simAutomated testsBalance tools

The key decision was that the game rules know nothing about graphics. The simulation is a pure, deterministic step at 128 ticks per second. Rendering, sound and the HUD only read it. That makes rounds reproducible, lets bots be balanced by simulating rounds headlessly, and keeps multiplayer simple, because the host runs the same simulation everyone sees.

What's in it

  • 3 maps (Foundry, Terminal, Skybridge), 5 agents with four abilities each, 9 weapons plus a blade.
  • A full 13-round match with side swap and overtime, a credit economy, and buy, plant and defuse phases.
  • Bots from Easy to Elite that trade kills, lurk and save. There's also a practice range with drills and live accuracy stats.
  • Fixed recoil patterns, movement inaccuracy, wall penetration, killcam, rebindable keys and career stats.
  • Audio is all generated in code: per-weapon gunshots, HRTF positioning, wall muffling, reverb and a menu music loop.
  • LAN multiplayer through a dependency-free WebSocket server.

Honest limits

  • Multiplayer has no client prediction or lag compensation. That's fine on a LAN, but not ready for the internet.
  • Feel (mouse, recoil, sound) was tuned more by numbers than by long playtesting.
  • The only downloaded art is a few public-domain (CC0) surface textures. Everything else is generated, which shows up close.

What I learned

Separating "what is true" (the simulation) from "what you see" (rendering) is what makes a complex real-time system testable. Without it, the only way to find a bug is to play until it happens.

Case study · 03 · FLL innovation project

ArchaeoSmart

Archaeological field teams record findings on paper, which is fragile, unstructured, and impossible to search or share. Our FLL innovation project was a tool that actually works in the field: offline, on a phone.

When
2025 – 26 season
Team
LOGIKO (I led a team of first-timers)
Result
1st place Morocco · FLL International, Houston
Stack
HTML/CSS/JS · PWA · Leaflet · Web Speech

What I built

A mobile-first Progressive Web App with voice-guided artifact recording, GPS geo-tagging, QR label generation and scanning, canvas drawing for site sketches, CSV export, a map view and a statistics dashboard. It's entirely client-side, with no server, and it works offline.

How the system works

Input

Voice answers, form data, GPS location, QR scans, canvas sketches

Storage

Artifact records are serialised locally, so the app keeps working without internet

Retrieval

QR codes and searchable IDs reconnect physical finds to their digital record

The main constraint was reliability in the field. The app had to keep collecting data when the network disappeared, so I treated offline behaviour as the core architecture, not a bonus feature.

Hardest challenge

The voice-guided form, where the app asks questions and you answer by speaking. Getting the Web Speech API to behave consistently on iOS and Android was brutal. Safari handles audio permissions completely differently from Chrome, and stopping continuous recognition from cutting off mid-answer took weeks of refinement. We got it working.

Limitations I'd fix

Data lives in localStorage and is lost if it's cleared. A production version needs a sync queue, a remote database, user accounts, and conflict resolution for two people editing the same artifact offline. I'd start with an event log, then compare it with CRDT-style merging if collaboration became central.

What I learned

Building something real forces you to understand things you'd never look up voluntarily. I had zero web experience when this started, and so did my teammates. Needing it to work in a field taught me more than any tutorial could.

Case study · 04 · Backend

Workspace OS

Every project I'd made before was purely frontend, with no database, no auth and no server. I knew that gap would limit me, so I built something specifically to close it.

When
2026 · built in one day
Why
Deliberate practice: learn how backends really work
Stack
Supabase · PostgreSQL · RLS · JavaScript

What I built

A multi-tenant SaaS workspace system with email/password authentication, workspace creation and deletion, roles (Owner vs Member), invite codes, projects and tasks with priority levels, and a full audit log.

System design

Entities

Users, workspaces, memberships, projects, tasks, audit logs

Relationships

Users join many workspaces; workspaces own projects; projects own tasks

Invariant

A user must never read or change data outside their workspace membership

Supabase handles auth and PostgreSQL storage. Row-Level Security enforces workspace isolation in the database, not only in the UI. The key insight was that permissions are part of the data model: if the frontend is bypassed, the database should still reject unauthorised access.

What I learned

The hardest part wasn't the code. It was thinking in data relationships. Who owns what? How do you stop a Member from deleting an Owner's project? Those aren't coding questions, they're systems design questions, and that shift in thinking was the whole point.

Tradeoffs & next step

Supabase let me learn auth, relational data and RLS quickly, but it ties the project to platform-specific policies. Next I'd add real-time collaboration, email invites, pagination for large workspaces, and server-side functions for actions that shouldn't live in client code.

Case study · 05 · 3D tool

PoseSandbox

Digital artists need fast 3D pose references, but most tools are expensive desktop software or clunky web ports. I wanted something that opens instantly, needs no account, and exports an image without friction.

When
2024 – 25 · my first website
Stack
Three.js · WebGL · transform controls

How the system works

UI layer

Tool buttons, mode switching, save/load, reference image controls, export

Interaction layer

Mouse input becomes 3D intent through raycasting, selection and transform controls

Render layer

Three.js scene, camera, lights, body parts, props and the redraw loop

ClickRaycastSelect jointTransformRenderExport / Save

The engineering problem wasn't displaying a 3D model. It was turning a 2D action (a click or a drag) into a predictable 3D manipulation, while keeping camera movement, joint selection and transforms from fighting each other.

Why Three.js

Raw WebGL would have meant spending the project on shaders and buffers. Three.js gave me a scene graph, camera controls, lighting and loaders, so I could focus on the harder product problem: making 3D interaction understandable to non-technical users.

Tradeoffs

The first version uses a hand-built joint hierarchy instead of a full skeletal rig. That made it buildable as a first 3D app, but rotations can feel mechanical, and complex poses need more manual work than inverse kinematics would.

What I learned

Interactive tools are mostly state problems: what's selected, which mode is active, whether you're moving the camera or the model, and what gets saved. Confusing internal state creates a confusing user experience.

What I'd do differently

I'd use a real skeletal rig with inverse kinematics, add undo/redo through state snapshots, separate rendering logic from UI logic more cleanly, and add performance guardrails for heavier scenes.
